# Decisions

Reasoning that is not in the code. Newest last.

## 2026-10-30: a repo beside cinder, format crates by path

The plan's prerequisite was a second workspace inside the cinder repo sharing its `crates/`. This is a separate repo instead, with `csl-run` and `pgm` as path dependencies on `../cinder/crates/`. The format stays one implementation, which is what the prerequisite was for; the repos stay separate because cinder is a closed PoC with its own chain, harness and results, and the Ethereum work should not churn its history. Cinder has no remote today, so a path dependency is also the only one possible; when either repo gets a remote the dependency becomes a git revision, and a published crate is the end state. `cargo fmt --all` here reaches into the path dependencies and reformats them in rustfmt's default width, which is not cinder's style: run it, then `git -C ../cinder checkout -- .`, or format single files.

## 2026-10-30: the trie crate, before anything else

The profile's claim that needed testing first was "absence from the trie alone, for every shape of miss", and it depends on a builder that emits every node at its position and a walk that returns the shape. `csl-eth-trie` is that, with no file format in it. The builder streams sorted leaves with a stack of open branches; a node is emitted when it closes if its RLP is 32 bytes or longer (or it is the root), and embedded in its parent otherwise, exactly where alloy's `RlpNode::from_rlp` embeds it, so the roots agree with `HashBuilder` on uniform tries from 2 to 5,000 leaves and on crowded tries where leaves, extensions and branches fall under 32 bytes. The walk fetches hashed children by `NodeKey::prefix(path, depth)` and checks keccak before decoding; embedded children are decoded in place under the parent's hash. Every emitted node is on some leaf's walk and every walk touches only emitted nodes, checked in `tests/roundtrip.rs`. A node deeper than 62 nibbles cannot be keyed (`TooDeep`), which the producer treats as an abort; real keccak paths never get there and the synthetic tests had to be told so.

## 2026-10-30: `csl-run` grew the variable layout, in cinder

Core §3.2's variable layout and `inline_proofs = false` are implemented in cinder's `csl-run` (its `docs/decisions.md`, same date), additively: `Format { layout, inline_proofs }`, `with_format` constructors, `Page::encode_with` / `decode_with`, `Layout::try_new_with`, `Reader::get_entry`; `pgm` gained `Grouper::push_at` and `Fitter::finish_with` because a variable run knows its page count only when the last page closes. v1-min's signatures and `Lookup` are unchanged and cinder's chain passes. A variable layout with inline proofs is refused by the writer: a record's size would depend on the page count. The run's identity is `blake3` of the file, computed by a read-back pass at `finish`. Conformance vectors and the TypeScript harness do not cover the variable layout yet; they are this repo's to add once the format settles on mainnet shapes.

## 2026-10-30: blob threshold 3,968, not the profile's 4,096

A tag 0 value alone on a page can be at most `4096 − 66 − 2 − 32 − 1 − 2 = 3,993` bytes (`csl_run::MAX_INLINE_VALUE`). Core §3.2 says blobs start above 3,968; the profile's "4,096" cannot fit a page. `CODE_BLOB_THRESHOLD = 3968`. The profile text should be corrected to core's figure.

## 2026-10-30: the manifest is JSON and nothing signs it

Cinder's `Manifest` and `ColdRoot` carry base, delta and rebuild semantics and a sealer signature, none of which applies: nothing anchors a run root on Ethereum and the client's single trust input is the `state_root` it verified. The snapshot manifest (`snapshots/<block_hash>/manifest.json`) names the execution block hash, number, timestamp, `state_root`, the covered prefix, and one `RunRef` per non-empty table (`csl_run::RunRef` with `block_lo = block_hi = block_number`). `snapshots/latest` holds the newest block hash. `Snapshot::open` takes the caller's verified `state_root` and refuses a manifest that claims another, rather than walking files that cannot verify and reporting them `Insufficient` one key at a time. An empty table has no run (csl-run's rule), so a slice without code or storage has three files, not four; the client answers `NoTable` for it.

## 2026-10-30: the producer sorts in memory

Nodes are collected in vectors and sorted before writing: a 1/256 mainnet slice is a few million nodes, a few GB at most, and the milestone 1 machine has 64 GB. Milestone 4's full export (about 1.5 × 10^9 nodes) needs the external sort cinder's sealer already has, behind the same `produce` call. The producer checks every storage root against its account's leaf, the account root against the header's `state_root`, every `codeHash` against its bytecode, and writes nothing until all three hold; an account with no storage stream must carry the empty root. The content-addressed fourth table (`keccak(node) → node`) is written from the same nodes, deduplicated, for the serial baseline of profile §9, but no client reads it yet.

## 2026-10-30: what the first end-to-end run measured

`crates/client/tests/e2e.rs` on 3,000 synthetic accounts (leaves at depth 3, so speculation to depth 9 wastes six lookups per read; mainnet leaves sit at 7 or 8 and waste two).

- **Every shape.** 3,000 present accounts verified; 1,000 random absent keys split 608 `EmptySlot` and 384 `LeafMismatch`, plus a crafted 60-nibble extension giving `ExtensionMismatch`, `EmptySlot` under its branch and `LeafMismatch` at its leaf; 19,968 present storage slots and an absent slot per trie; empty storage answered without a storage request; code inline (375) and as blobs (375); `KECCAK_EMPTY` with no fetch; an unknown `codeHash` is `Insufficient(Missing)`.
- **Faults.** 40 random bit flips per table in six rounds, a truncated table, a dropped page served as a short read, a table from a different trie under the real `state_root`: every read was the right answer or `Insufficient`, none was a false absence or a wrong value. A table the manifest names but the bucket lacks fails `open`.
- **ε against requests.** The reader's walk after a prediction is sequential: each page the prediction is off is a dependent request. With the same 170-page account table, ε = 1 (model 172 B) gave a mean 14.2 requests and 58 KB per present account read over ten speculated depths, 1.42 per lookup, every walk one page; ε = 2 and ε = 4 both fit one segment (28 B) and gave 16.5 requests and 68 KB, 1.65 per lookup, with walks of up to 4 pages. The profile's "about nine page requests, 40 KB, one round" assumed a direct hit per depth. Consequences: `produce` takes ε as an option and the default stays the profile's 4 until mainnet shapes are measured; the client should learn the leaf depth from its first reads and stop speculating past it; and for the deepest depths a two-page range (`p`, `p + 1`) buys subtree contiguity for one request. The 50 KB budget is not asserted by the tests; it is milestone 1's exit on real shapes.

## 2026-10-30: range proofs are verified by rebuilding, and the proof is the boundary

A snap `AccountRange` response is consecutive leaves from `origin` plus the Merkle proofs of the origin path and the last leaf's path. The usual verifier (geth's `VerifyRangeProof`) stitches the proof nodes around the leaves and hashes up. `csl-eth-trie` instead reads the two proof paths once, collecting the child references that stand for everything *left* of `origin` and *right* of the last leaf (`walk_side`), and feeds those references and the leaves through the same streaming builder that produces runs, now able to `push_sealed(path, RlpNode)`: a sealed subtree is a parent's child slot standing for a subtree whose contents are not here. The rebuilt root must equal `state_root`; the slice is `more` when anything is sealed to the right. One builder for production and verification is the point: the sealed references the verifier collects for the first and last chunk of a slice are exactly the boundary the producer needs to build the slice's leaves up through the ancestors to `state_root`, so `ProduceOptions::boundary` takes them unchanged and the producer's existing root check becomes the slice's proof of membership. The ancestors emitted are the root, the branch at each depth along the prefix path, and the branch the first leaf past the slice hangs under (snap returns that leaf, the slice drops it, its sibling reference is kept). Keys outside the prefix walk to a sealed slot and end `Insufficient(Missing)`, never in an answer: `crates/client/tests/slice.rs`. A sealed path nested inside another, or out of order, is refused by the builder; a boundary with a reference altered or dropped fails the `state_root` check.

## 2026-10-30: snap/1 and snap/2 both offered, eth and snap multiplexed by hand

reth 2.9.0's `EthSnapStream` requires exact snap/2, but mainnet peers still answer snap/1 (geth 1.16, Nethermind 2.2 in the first probe), and the six message ids are the same in both. The peer offers eth/68, eth/69, snap/1, snap/2 in `Hello`, takes whatever is shared, and drives the `P2PStream` itself: eth frames from id 0, snap frames from `eth.num_messages()` as reth's `relative_message_id_offset`, snap's own id byte rebased on the way out. Inbound requests from the peer (headers, bodies, transactions, receipts, snap) are answered empty so the connection stays useful; everything undecodable is ignored rather than fatal.

## 2026-10-30: the pivot is self-consistent, not yet verified

The fetcher pivots on the first usable head a peer announces: the peer's `Status` block hash, the header fetched by that hash, checked to hash to it, and recent (number past the fork head and timestamp within fifteen minutes; a syncing geth announces genesis). That ties the slice to a header some peer claims is canonical, not to a verified one. The head verifier over light-client files (`helios-consensus-core`) is the next piece; until then a slice's `head.json` is "the state at this hash as the network served it", and the producer's `state_root` check is the only verification. `--pivot <hash>` exists so a run can be pinned to a hash chosen out of band.

## 2026-10-30: re-pivot keeps storage and code by their own roots

snap peers serve roots from about the last 128 blocks. A 1/256 slice at today's state is tens of thousands of requests, more than a window at a moderate peer count, so the fetcher expects to re-pivot: when three peers (or every connected peer) answer an account range with "no such root", the pivot moves to a fresh head, every account sub-range starts over, and the storage tries and bytecodes already fetched are kept, keyed by storage root and code hash respectively, since they are content-addressed and an unchanged account still references them. Only account ranges are redone. Account ranges are split sixteen ways on the nibble after the prefix so eight peers work in parallel on one root; a sub-range's chunks are contiguous, so its left and right boundaries are the first chunk's left and the last chunk's right.

## 2026-10-30: the slice on disk is separate from the bucket

`csl-eth fetch` writes a slice (`head.json`, RLP files of accounts, storage by root, code, and the boundary) and `csl-eth build` turns it into a bucket. Two steps because fetching takes minutes to hours and depends on the network while building is deterministic and seconds; a slice can be rebuilt with another ε or table layout without re-fetching, and the measurements of milestone 1 compare builds of one slice.

## 2026-10-30: the first mainnet slice, and what it cost to read

`csl-eth fetch --prefix 1a7` (1/4096 of state) at block 26,305,903, state root `0xe8e6…5800`, from one Nethermind peer: 104,361 accounts, 3,362 distinct storage tries (6,878 by account; proxies share roots) with 129,555 slots, 2,168 bytecodes, 17.9 MB over 133 requests, no re-pivot. Transfer took about two minutes; the other two were spent finding a peer. Getting peers is the slow part: of 355 dials in a 100 s probe, 155 answered "too many peers", 81 timed out, 58 reset, 21 had no snap, and 3 handshook. Dials now run 192 wide with a 10 s dial timeout, candidates are deduplicated by address as well as node id (a crawler answers from one address under fresh keys), and an idle peer is kept polled so its pings are answered; before that, geth dropped us for "ping timeout" while we waited for a pivot. A syncing peer announces genesis as its head and is not a pivot candidate.

`csl-eth build` turned the slice into a bucket in 0.4 s with 102 sealed subtrees in the boundary and the account root equal to the header's `state_root`: the slice is the network's state at that block, proven. 144,964 account nodes in 5,557 pages (22.8 MB), 180,808 storage nodes (20.3 MB), code 1.4 MB plus 407 blobs, the content-addressed table 42 MB. Mainnet account leaves sit at depth 8 (9 nodes walked, p95 10), storage leaves 10 to 12 nodes deep under the account.

`csl-eth check` reads the bucket with the client, 300 sampled accounts with their slots and code, absent keys inside the prefix, keys outside. Every value verified, every inside absence was proven by the trie, every outside key ended `Insufficient(Missing)` after a repair round at the sealed slot, at every ε. The cost, mean per account read, speculating depths `0..=8`:

| ε | model | requests | KB | slot read requests / KB |
|---|---|---|---|---|
| 1 | 3,076 B | 13.4 (p95 16) | 53.5 | 25.4 / 101 |
| 2 | 748 B | 18.7 | 74.6 | 32.5 / 130 |
| 4 | 220 B | 27.0 | 108 | 46.3 / 185 |
| 8 | 52 B | 41.0 | 164 | 78.1 / 312 |
| 16 | 52 B | 61.5 | 246 | 111.5 / 446 |

Speculating to depth 9 instead of 8 adds about 1.4 requests and 5 KB. The profile's "about nine page requests, 40 KB, one round" is not met by any ε: the rounds are right (1.0 to 1.1), the requests are not, because each page of model error is a dependent request on the sequential reader, as the synthetic run already showed. ε = 1 is now the default: its model is 3 KB for 145,000 nodes, which is nothing. The remaining gap to the profile's figure is the lookups themselves, nine per read, and that is where the next client work is: the top levels of the trie are the same nodes for every key (one root and one node per depth along the prefix here; 1 + 16 + 256 + 4,096 nodes for the top four levels of full state), so a client that keeps them after its first reads speculates from depth 4 and pays five lookups, and a `(p, p + 1)` range for the deep depths buys a prediction miss for one request. Both are measurements for the next stage, not changes to the format.

## 2026-10-31: the per-snapshot budget, and what the HTTP bucket showed on loopback

Two budgets, not one. Resident memory for a light client can be a few MB without anyone noticing; what cannot is bytes per snapshot for a client that follows the chain, because the model changes with every snapshot and milestone 2 snapshots every finalized checkpoint, about 225 a day. Extrapolating this slice's model bytes per page (0.55 at ε = 1, 0.13 at ε = 2, 0.04 at ε = 4) to mainnet's roughly 16 million account pages and 65 million storage pages gives models of about 45 MB, 11 MB and 3 MB per snapshot. The plan now says: under 1 MB per snapshot for a following client. ε = 1 stays the default because its model need not be downloaded whole: the keys are keccak hashes, so the model's segments are nearly evenly spaced in key space and the section covering a key can be predicted from the key and fetched as one small range in the same round as the pages. That is a reader change in csl-run, not a format change, and it is the next client lever to build.

`csl-eth check --url` reads a bucket behind HTTP (`HttpBucket`: files by GET, runs by `Range`, an optional proxy for tunnelled hosts). A `Prefetch` hint on the source lets the snapshot hand it the predicted page of every speculated depth before the round, fetched over threads; a source keeps one read's pages and forgets them when the next read starts (`forget`), so nothing is cached across reads and every read is measured on its own. R2 is not enabled on the account and writes to fafo-0 were not permitted in this session, so the measurement so far is loopback through caddy, which says nothing about latency (0.4 to 1 ms per read) and everything about requests on the wire:

| account read, ε = 1, depths 0..=8 | HTTP requests | KB | dependent requests after the round |
|---|---|---|---|
| sequential, pages kept for the read | 6.7 (p95 8) | 27 | all 6.7 |
| prefetch the predicted page per depth | 6.7 (p95 8) | 27 | 1.3 (p95 3, max 3) |
| prefetch predicted ± 1 | 12.0 (p95 13) | 48 (p95 52) | 0.0 (max 1) |

The reader's logical count was 13.4 lookups; on the wire it is 6.7 pages, because the table's order is pre-order: a node's key is its path, so a node sorts immediately before its subtree, the depth-7 node and its sixteen depth-8 children share a page, depths 5 to 8 of one path sit within a few pages, and in a slice the ancestors above the prefix sit together on the first page. The reader has no page cache, so before this it fetched the same page once per depth. Prefetching one page each side of every prediction makes the read one round for 12 requests and 48 KB, which is the profile's "one round, 40 KB" within a few KB on mainnet shapes; the mean is under the 50 KB rule and the p95 is not. Storage reads are over it: 19 requests and 76 KB sequential, 36 and 146 KB at ± 1, because the slots sampled sit 10 to 12 nodes deep in the largest contracts. Still to measure, in order: a two-page range (`p`, `p + 1`) per prediction as one request, which should give one round at about 5.5 requests and 44 KB; the model section by key; the top levels kept across reads; and all of it against a remote host, where the rounds become milliseconds.

## 2026-10-31: the same reads against R2, where the rounds become milliseconds

The ε = 1 bucket (413 files, 90.7 MB) is on Cloudflare R2 behind its r2.dev domain, bucket `csl-eth-apac`. The first attempt landed in WEUR because the location hint was a guess; a deleted bucket's name keeps its old region when recreated, so the APAC bucket has a new name and `csl-eth` is retired. The client ran on a Mac in Taipei behind a Mullvad exit in Manila, served by Cloudflare's Hong Kong colo: one range request is about 110 ms at the median (the outside-prefix reads, one page each, measure it), which is a slow path, not a fast one, and that is the point of the table. 40 to 60 sampled accounts per mode, speculating depths `0..=8`, every value verified, zero wrong or unexpected:

| account read, ε = 1 | HTTP requests | KB | dependent | ms p50 | ms p95 |
|---|---|---|---|---|---|
| sequential | 6.3 | 25 | 6.3 | 829 | 1,110 |
| prefetch the predicted page per depth | 6.9 | 28 | 1.4 (max 3) | 286 | 506 |
| prefetch predicted ± 1 | 12.1 | 50 | 0.0 (max 1) | 179 | 936 |

Storage slot reads, two samples each, deep slots in large contracts: 4.1 s sequential over 19 requests, 1.1 s with the predicted pages prefetched (5 dependent), 0.8 s at ± 1 over 38 requests and 150 KB. Code: one or two requests, 100 to 200 ms.

What it says. Sequential reading is the round-trip count times the round trip: 6.3 requests at about 130 ms is the 829 ms seen, and nothing about the format fixes that, only fewer dependent requests do. Prefetching the predicted page takes the dependent chain from 6.3 to 1.4 and the read from 829 to 286 ms, without a byte more on the wire; the remaining 1.4 are model misses at the deep depths, and they cost a round each. Prefetching ± 1 removes the last dependent round for 22 KB more and gets the median to 179 ms, about 1.6 round trips: one for the parallel fan-out and the rest is the slowest of 13 connections. Its p95 is worse than the predicted-page mode's, 936 against 506 ms, which the loopback run could not show: the fan-out is 13 parallel HTTP/1.1 requests on 13 connections (ureq has no HTTP/2), so one slow connection, or a fresh TLS handshake through the VPN, holds the whole round. The lever here is not fewer pages but fewer connections: HTTP/2 multiplexing, or the two-page range per prediction that halves the request count to about six for the same bytes. Both are client changes; the first is a dependency choice, the second was already next on the list and now has a second reason.

Against the budgets: 50 KB per account read at ± 1 is the profile's figure on mainnet shapes, and 180 ms through a VPN to another country is a read a wallet can wait for. Storage is still three times over, and it is the depth of the slots, not the format, which the top-level cache and the two-page range should both help. The one-round claim is now measured end to end: a client with the model in hand reads any account in the slice in one parallel round against a public bucket, with no node anywhere.

## 2026-10-31: merged ranges and the top-level cache, against R2

Two client changes, no format change. The hint now asks for touching pages as one `Range` (the depths of one path share pages in the pre-order table, so a read's pages come in a few runs), and the HTTP source serves any page out of a range that covers it. And the snapshot keeps the account trie's nodes at depths below `top_levels` once a verified walk has passed them, gaps included (an extension spanning a depth is also a fact worth not refetching); those depths are neither hinted nor fetched again. The cache is the snapshot's and dies with it, since every block rewrites the top of the trie. Only nodes above the deepest node fetched are kept, because those are the ones the walk hashed; an `Insufficient` read keeps nothing. Same bucket on R2, same Mac in Taipei through the VPN, 60 accounts per mode, every value verified:

| account read, ε = 1 | HTTP requests | KB (p95) | dependent | ms p50 | ms p95 |
|---|---|---|---|---|---|
| ± 1, one request per page (before) | 12.1 | 50 (56) | 0.0 | 179 | 936 |
| ± 1, touching pages merged | 3.8 | 49 (56) | 0.0 | 136 | 329 |
| ± 1 merged, top 4 levels kept | 2.8 | 37 (44) | 0.0 | 131 | 215 |
| above only (p, p + 1) merged, top 4 | 3.6 | 29 (36) | 0.8 | 200 | 477 |
| below only (p − 1, p) merged, top 4 | 3.5 | 28 (36) | 0.7 | 206 | 466 |
| predicted page only, top 4 | 4.4 | 20 (28) | 1.5 | 310 | 518 |

One range request through this path is 105 ms at the median (the outside-prefix reads measure it). An account read at ± 1 merged with the top four levels kept is 131 ms: one round trip and a quarter, three requests, 37 KB, 44 KB at p95. That is the profile's row, "at most 50 KB and two network rounds", met at the p95 and not only the mean, on mainnet shapes, against a public bucket. Merging alone took the tail from 936 to 329 ms, which confirms that the tail was connections, not pages; the cache took another 12 KB and the last connection off.

The asymmetric ranges answer a question: the model misses both ways. A one-sided two-page range leaves 0.7 to 0.8 dependent requests either way, and each costs a round trip, so the read is slower (200 ms) for the 9 KB saved. The ε = 1 model is off by one page about equally often in either direction, and ± 1 is what buys the single round. Predicted page only is 20 KB and 310 ms: the cheapest in bytes, the slowest in time, 1.5 dependent requests. The trade is now measured and ± 1 merged is the default to recommend.

Storage slot reads, two deep samples: 12 requests, 138 KB, 0.66 s at ± 1 merged with the cache (the cache is the account trie's only). Still three times the budget, and the next lever for it is the same one as for the model: sections by key, so that storage and account speculation share a round, plus a per-contract top cache for the storage tries a client returns to. The top-level cache at full state: depths 0 to 3 are 4,369 nodes, about 2 MB per snapshot if all are touched, which a client fills lazily from its own reads, so a wallet that reads a hundred accounts a day holds a few hundred of them.

## 2026-10-31: the head from files, and why the fetcher now holds its peers

The slice so far verified against a state root the fetcher took from a peer's header: the reads were proven, the root was not. Profile §3 closes that with the beacon light-client protocol published as files. The producer writes `head/bootstrap/<root>`, one `head/updates/<period>`, and `head/finality`, each the beacon API's own JSON response with its version envelope, so any node's endpoint can be mirrored byte for byte. The client's trust input is one weak-subjectivity checkpoint root; from it the bootstrap proves the first sync committee, each period update hands over to the next committee under the current one's signature, and the finality update's signed header carries the execution block hash and state root. The verifier is `helios-consensus-core`, wrapped in `csl-eth-head` behind a `HeadSource` trait (a directory, the HTTP bucket, a test map), so a finality-proof verifier can replace it later without the client noticing. Tests run on real mainnet objects of 2026-10-31 with `now` pinned: the honest set verifies to block 26,310,853 with 511 of 512 signers; a wrong checkpoint, a forged execution state root or block hash, too few signers, one flipped signer bit, an update in another period's slot, a clock a day behind, and a file that is not the object are each rejected with the error that names the step. A frozen `head/finality` is not an error but lag, which the client sees as `finality_lag_secs`; a producer can withhold, it cannot forge.

The client side is `open_at_head`: verify the head, require `snapshots/<finalized block_hash>/manifest.json` to exist, open the snapshot at the head's state root. Without the snapshot it fails with the finalized block and the newest snapshot's block, not with a read against an unproven root. `check --checkpoint <root>` runs the same path on the CLI and refuses a slice whose root differs from the finalized one.

That requirement moved the fetcher's problem. A finalized block is 13 to 19 minutes old when its finality update appears, and peers serve snap for about 128 blocks, 25 minutes, behind their head, so a fetch at the finalized root has six to twelve minutes, and it cannot start looking for peers after the root is known. The first fix was a hold mode (`--pivot-file`: dial first, take no peer's head as pivot, read the hash from a file when it appears). It was not enough, and the reason is worth writing down. A debug run of three minutes made 804 dials: 388 were refused with "too many peers", 156 timed out on stale discovery records, 94 were reset, 55 offered no snap, a few dozen were other chains. Of the peers that did accept, Nethermind culled us with "too many peers" after 20 seconds, Besu with "useless peer" (its peer validators ask a new peer for specific historical headers, which a client with no history cannot return), and geth closed after about 30 seconds; the rest were a crawler. The same loop from fafo-0, a datacenter IP with no VPN, got 5 accepts in 2,270 dials over 36 minutes, so it is not the network path: mainnet nodes are full, and a fresh node with no history and nothing to serve is the first one dropped. Peers cannot be held; they can only be used in the seconds they are there.

So the fetcher stopped racing finality. The finalized checkpoint is always the first block of an epoch, and the time of that slot is known in advance: `--pivot-at next` computes the next epoch boundary, holds whatever peers it has, and once the boundary passes asks each peer for its head and steps to the block whose timestamp is the boundary (or the block before a missed slot, recognized when the block after it is seen). The fetch then runs with the whole snap window ahead of it, and the producer loop waits for the finality update to name the hash before writing the head files; `check --checkpoint` refuses the slice otherwise. Nothing new is trusted: a peer could answer a by-number request with any header, and finality is what proves it 13 minutes later. First run, 2026-10-31, from the Mac and from fafo-0 at the same time: both pivoted on block 26,311,778 (the Mac 24 seconds after the slot through a geth peer that had announced the block before; fafo-0 two minutes later through another), both fetched the 1/4096 slice in 14 to 24 seconds (104,411 accounts, 129,606 slots, 2,172 codes, 17 MB, about 135 requests, 2 to 3 peers each), the same hash on both, and the finality update at 09:27 UTC named it. The head files written then verify to that block, so the bucket's `snapshots/<hash>` is the state the finality proof commits to. A real producer with its own node has none of the peer problem; what carries over is the shape of the loop, fetch at the epoch boundary and publish when finality names it, and the client's rule that a snapshot without a finalized root is not a head.

The bucket built from that slice went to R2 beside its `head/` (417 files, 44 seconds), and `check --url ... --checkpoint <root> --prefetch 1 --top-levels 4` from the Mac read it through the head: verifying the head cost 5 requests and 117 KB (bootstrap 54 KB, the period's update 57 KB, finality 5 KB, the manifest), once per session; then 61 accounts at 2.8 requests, 37 KB (44 at p95), 148 ms p50 and 260 p95, absence inside the prefix at the same cost, outside at one request, storage slots at 10.5 requests and 126 KB, every value verified, 0 wrong. The same figures as yesterday's slice within noise, now against a root the finality proof commits to rather than a peer's word.

## 2026-10-31: the client in the browser

The demo is static files plus a browser, so the client now runs in one: `crates/wasm` compiles `csl-eth-client` and `csl-eth-head` to WebAssembly behind wasm-bindgen, and `browser/` is a page that opens the R2 bucket through the head and reads accounts, storage and code, showing each answer's status and what it cost. It is deployed at https://csl-eth.indigo-db8.workers.dev (a static-assets Worker, `browser/deploy/`, deployed with `cf deploy`) and reads the public R2 bucket directly, so the page is the whole trust boundary: nothing on the JavaScript side verifies anything, it transports bytes and renders.

The read path stayed synchronous. The client is a hint, then the fetches the reader asks for as it walks, and making that async would have meant rewriting `csl-run`'s reader and the walk for one platform. Instead the client runs in a module Web Worker, where a synchronous `XMLHttpRequest` with a `Range` header is allowed, and the wasm bucket calls `globalThis.cslFetch(url, offset, len)` for every file and range. This is the cinder browser client's design and it carried over whole: one JS function, a bucket and a run type over it, counters and a request log the page reads after each call. The costs of that choice are one request at a time (a hinted round's merged ranges are fetched sequentially, so a read with three ranges pays three round trips where the CLI pays one; parallel ranges need the main thread's `fetch` and a `SharedArrayBuffer` handshake, which needs cross-origin isolation, left for a later version), and R2 refusing multi-range requests (400), which is why the ranges are separate requests at all.

What it took to compile: getrandom 0.3 wants `--cfg getrandom_backend="wasm_js"` (`.cargo/config.toml`) and its `wasm_js` feature; helios's clock is a different type on wasm, so the head crate computes the current slot itself from the genesis time; the client's directory bucket is gated off wasm32; and blst, under helios's signature check, needs llvm-ar rather than Apple's ar to archive for wasm32 (`scripts/build-wasm.sh`, pinned in `mise.toml` with wasm-bindgen-cli at the crate's exact version). The module is 1.17 MB, 316 KB gzipped, most of it the BLS verification; it loads in about 0.7 s.

The sequential requests show: the CLI's 131 ms account read is 2.8 requests in 1.25 round trips, the page's 300 to 560 ms is the same requests one after another. Parallel prefetch is the next lever for the page specifically, and sections by key the next for both.

## 2026-10-31: the client does no I/O, and a round is a round everywhere

The browser entry showed the cost of the inherited design: a client that reads synchronously as it walks has to live somewhere synchronous reads are allowed, and in a browser that is a worker with one `XMLHttpRequest` at a time, so a hinted round of three ranges was three round trips. The planned fix was a `SharedArrayBuffer` handshake to the main thread's `fetch`, which is a hack on top of a shortcut; Indigo asked why anything was synchronous at all, and the honest answer was that nothing needed to be. The client now does no I/O. `csl-eth-client::store` holds what has been fetched (whole files for the store's life, byte ranges for one read) and the `Want`s the computation noted on its way. `try_account`, `try_storage`, `try_code` and the openers compute over the store and return `Pending` when something is missing; the host takes the wants, fetches them however it likes, supplies the bytes, and runs the computation again. A `Driver` is the synchronous host (a directory; HTTP over scoped threads), behind the unchanged `account` / `storage` / `code` signatures; the browser is an asynchronous host and drives the same loop with `Promise.all`. The `Prefetch` trait, the `Bucket` trait, the per-source range caches and the HTTP counters that distinguished hinted from dependent requests are gone: what the walk wants and what goes on the wire are now the same list, so `Cost.requests` and `Cost.rounds` are exact rather than reconstructed.

The trick that kept `csl-run`'s reader untouched is replay: each round the read starts over from its first step, and because the store only grows within a read, it gets at least as far as the last time. A reader's `fetch_page` on a page the store lacks returns an `Io(WouldBlock)` the client recognises as pending; the pending is collected across every depth of the speculative round, not raised at the first, so a round carries everything the round needs. The speculative round asks for the model's predicted page at every depth the walk may touch, widened by the `Hint` (pages below and above, touching pages as one range), plus the storage trie's predicted pages when the read is a storage read, since the storage table's keys need only the owner, not the account's storage root: storage speculation in the account's round, which was on the list, fell out of the shape. Repairs want the missed node's predicted pages and are rounds only when the store does not already have them; a repair served by a neighbouring depth's range costs none. Opening is rounds too: the head's bootstrap, update and finality files are sequential by nature (each proves the next), then the manifest, then every table's model in one round. A table whose model does not verify or whose file is short does not refuse the snapshot: its reads are `Insufficient` with that error, and the other tables serve, which is what the fault tests expected of the lazy loading before.

The rounds a read takes are now visible, and the first thing they showed is that the default of "predicted page only" is not one round: the model's bound is ε pages, the reader walks up to ε + 1 in the fence direction, and each step beyond the hinted span is a dependent round trip. The tests state it: with the hint set to ε + 1 around every predicted page, every present and absent read in the synthetic worlds is one round and the crafted pair's two repairs are at most two more. The CLI's `--prefetch` is that span, 1 by default in the measurements below because ε = 1 is what the tables were built with. One more browser fact: Chromium holds a cache lock per URL, so parallel `fetch`es of ranges on one run file were queued behind each other until `cache: "no-store"` bypassed the cache; that single option took an account read from 478 to 121 ms.

Measured against R2 through the VPN, both hosts, the same bucket at block 26,311,778 through the head. CLI, `--prefetch 1 --top-levels 4`, 61 accounts: 2.8 requests, 37.7 KB (45 at p95), one round every time, 120 ms p50 and 196 p95 (yesterday: the same requests in 1.25 rounds, 131 to 148 p50, 215 to 260 p95); absence inside the prefix the same; outside, one request and 101 ms; code 1.1 requests, 103 ms; storage slots 10.3 requests, 128 KB, one round, 299 ms (yesterday 660 ms in several). Browser, deployed page, Playwright: the head in 8 requests and 5 rounds, 126 KB, about 1 s; an account in 2 to 4 requests and one round, 28 to 48 KB, 120 to 310 ms (yesterday 290 to 560 ms sequential); a storage slot in 10 requests and one round, 124 KB, 250 to 310 ms (yesterday 0.7 to 1.3 s). The page and the CLI are now within noise of each other, which is the point: the client is one thing, the host decides how the round goes out. The `need` lists are also the natural event stream for the visualizer Indigo wants: each round is a list of ranges on named files, each answer a verified walk, and nothing else happens.

## 2026-10-31: the model is fetched by key, and the per-snapshot budget is met by construction

The slice's four models are 11 KB at ε = 1 (0.5 bytes per page), which is 45 MB per snapshot at full state: the one part of a read that scaled with the state instead of with the key, and the thing the 1 MB-per-snapshot budget was set against. The fix is in the format, in cinder's `csl-run` (its `docs/decisions.md`, same date), and it is the same move the pages made: the segments are stored as 4 KB **model pages** under a `bmt` tree, page 0 of the run carries a **top model** (a `pgm` fit over the model pages' segment starts) and the tree root, and `model_root` is `blake3` of page 0. The reader's prediction becomes a two-step lookup, top predicts a model page, the page predicts the data page, with the model page proved against the root and walked by its `k64` fences exactly as data pages are walked by theirs. `RunRef` and the manifest are unchanged; `csl-eth-store` writes every table in `RUN_FORMAT` (variable, no proofs, paged) and bumps the manifest's `format_version` to 2, which the client now checks.

The client needed little: `Opener` calls `Reader::prepare` (page 0 of each table in the open's one round, 16 KB for the four, where the whole models were 11 KB on the slice and would be 45 MB at full state) and `want_pages` asks `Reader::predict_page` instead of the model. When the key's model page is not in the store, the prediction is the read that notes the want, the key gets no data pages that round, and the next round has them: a cold neighbourhood costs one round and one 4 KB model page before its data pages, a warm one costs nothing more than before. `Cost.model_pages` counts them per read, the CLI and the page show them. The `top_levels` cache and the model pages compound: on the pre-order account table a path's depths 0 to 2 sit at the start of their 1/16, 1/256 and 1/4096 stretches of the file and so, at full state, on their own model pages (273 pages for all of them, shared by every read), while depths 3 and deeper share one or two; the cache answers the shallow depths, so a cold account read at full state is about two model pages and a warm one none. At slice scale every table but `nodes_by_hash` is one model page, so the slice exercises the mechanism (page 0, proof, fences, the cold round) and not the fan-out; `csl-run`'s tests do that on a 150,000-entry run at ε = 0 with a dozen model pages.

Measured against R2 from the Mac (direct this time, the Mullvad exit was off), release CLI, `--prefetch 1 --top-levels 4 --checkpoint`, 150 sampled accounts, 508 reads, every value verified, 0 wrong: accounts 2.7 requests, 36.6 KB (44 at p95), one round every time but the first (2 rounds, 1 model page), 135 ms p50 and 372 p95; absence inside the prefix the same; outside one request and 107 ms; storage slots 10.8 requests, 130 KB, 179 ms p50 (one cold read at 2 rounds and 605 ms), code 1.1 requests and 112 ms. The p95s carry a few network spikes of 2 to 3 s that hit one-request reads too. The page, redeployed on the rebuilt bucket (the same `snapshots/<hash>` keys overwritten, page and client in lockstep): head 8 requests in 5 rounds, 132 KB; the first EOA 5 requests in 2 rounds, 52 KB, 364 ms, "1 model page fetched"; the contract after it 2 requests in 1 round, 28 KB, 101 ms; the storage slot 11 requests in 2 rounds (cold), 128 KB, 392 ms, then the empty slot 10 requests in 1 round, 255 ms; console clean. The per-snapshot download of a following client is now page 0 per table plus the model pages of the neighbourhoods it reads, 4 KB each: for a wallet with a dozen accounts under 100 KB at full state against the 1 MB row, by construction rather than by measurement, since the slice has nothing to fan out over. What the slice cannot show and milestone 4's full export will: the top model's segment count at 2,700 model pages (it has 166 to spend, with `ε_top` doubling as the escape), and the real cold-read model-page count on mainnet shapes.

## 2026-11-01: milestone 1's exit tests, and what the fault table taught

The PoC spec's milestone 1 is closed by two commands. `csl-eth workload` draws keys from the slice by the shape of the trie's answer (present accounts through extensions and below the speculated depth, absences by each of the three ways a trie says no, slots in the largest tries and in empty storage, inline and blob code, keys outside the prefix), predicts each walk offline from the sorted leaves, and runs every read in both modes, scoring against the slice. `csl-eth faults` wraps the directory driver in a faulting one: a clean walk records each read's nodes, and each fault corrupts only the page that holds one chosen node per read, cycling through depths and tables, so a pass means every depth of every table was attacked, not just the root. The write-up is `results/m1.md`, with the JSON beside it.

Three decisions came out of it. First, aiming matters more than the fault list: the first version corrupted whatever page a read asked for first, which on a cached client is always the account root, and passed for the wrong reason; a review caught it, and the fault table now reports per-table, per-depth coverage so the claim is checkable. Second, both commands must be able to fail for the right reasons, and a second review (omp, an OpenAI model) found three ways they could not. A fault that changed nothing still passed, so the table's pass is now safe (no false answers, control all correct) and exercised (every fault changed responses in every mode it applies to, aimed on 98% of the reads it could aim at and landed on 98% of its aims per table); a run at fault rate 0 is safe and fails. The workload dropped duplicate draws without replacement (9,962 of 10,000 present accounts) and never checked its shapes, so it now fills every quota and fails if the slice cannot supply a requested count or a required shape, unless `--allow-short` marks the run as a reduced measurement. And the wrong-run-page fault could read past the other table's data and count a short read as a caught foreign page; it now splices one whole foreign data page in. The scorers have their own tests that hand them wrong answers. Third, the manifest's per-table file hash stays informational. The client never checks it and should not: values are proven by the trie and the model by `model_root`, so a mirror serving altered run files is caught node by node, and checking the hash would mean downloading every file whole. A fence that narrows cannot misroute a read either, since every node is an entry and narrowed fences still cover every entry.

What milestone 1 could not do is score against `eth_getProof`: no free endpoint serves a proof 7,000 blocks back. The expected values are proven to `state_root` by the peers' range proofs at fetch time, which is independent of the producer; the oracle check is implemented and waits for a fresh fetch or an archive key.

## 2026-11-02: the producer loop, and why a snapshot lasts until period P+2

The snapshot on R2 stopped opening at 06:40 UTC today, as the last entry said it would. The reason is in the head, not the state: the verifier walks period updates from the checkpoint to the clock's period, and the committees it hands over to are what sign the finality update. A finality update signed in period P is checked against the committee of P, which the client holds once it has applied the update for P−1; while the clock is in P+1 the update for P+1 may be absent (the verifier allows the current period's to be missing, since it exists only once that period has an attested block), so the head still opens; once period P+2 begins the update for P+1 is required, and after it the client's committee is past the one that signed. So a frozen snapshot lasts from one to two periods, 27 to 55 hours, and the only fix is to keep publishing. `csl-eth produce` is the loop that does it, and nothing in it is new: it chains the steps that were run by hand on 2026-10-31.

A cycle picks an epoch boundary (at least `--lead-secs`, 2 minutes, ahead, and at least `--every-mins`, 60, after the last published one), dials from two minutes before it, fetches the slice with the pivot at that boundary, builds it into a local mirror of the bucket, waits for the beacon node's finality update to name that exact block hash, lays out the head files, verifies the mirror as a client would, publishes, and deletes what is beyond `--keep`. Each cycle is one JSON line on stdout and in `<work>/produce.log`; a failed one names its step and the loop goes on to the next boundary. Three things in it are choices rather than plumbing.

The finality update is watched from the start of the cycle, not after the fetch. A beacon node serves only its newest finality update, so the one naming our block is available for one epoch, 6.4 minutes, starting 13 to 19 minutes after the boundary; a fetch that took longer than that would find the window gone. A thread polls every 16 seconds and keeps every update by the block it names; the cycle fails when one names a later block number than ours without ours having been seen (finality moved past, or finalized a different block at our height), or after `--finality-wait-secs`. The bytes kept are the response's, unchanged.

The order of publishing is chosen so that a reader never follows a pointer to something not yet there: the snapshot's run files, then its `manifest.json`, then blobs not yet in the bucket, then the head's bootstrap (once) and the period updates whose bytes changed, then `snapshots/latest`, and `head/finality` last. A client starts at `head/finality`; until it is replaced the old head stands, and the old snapshot with it, so a cycle that fails half way publishes nothing a client can see except possibly `latest`, which a client reads only to explain a refusal. The state file (`<work>/state.json`) records each file as it lands, so a restart re-uploads neither blobs nor finished updates. Period updates are fetched when missing, when they are the current period's (the beacon node improves its best update until the period ends), and once more after their period closes; an update fetched after its period closed and published is final and never rewritten. The current period's update is republished when its bytes change; both versions carry the same next committee.

Collection deletes snapshots beyond `--keep` (3), oldest first, and any snapshot a failed cycle left part-published, never the one `head/finality` or `latest` names, manifest first so a half-deleted snapshot is not one a reader would try; locally it drops their mirror directories, built-but-unpublished snapshots, and slices nothing keeps. Blobs are left alone. They are content-addressed and shared across snapshots (408 for the slice, 4.9 MB), and knowing which ones no kept snapshot references means reading every kept snapshot's code table; at slice scale the waste is a few new blobs per cycle, and a mark-and-sweep can come when it is not.

The head opens in two rounds now, which the loop makes necessary rather than nice: with a fixed checkpoint the bucket gains one period update a day, and the opener asked for one per round. Round 1 asks for the bootstrap and `head/finality`; round 2 for every update from the bootstrap's period through the clock's, once the bootstrap has proven the checkpoint (`csl_eth_head::update_periods`). The verifier then reads them in its order from the store; every rejection test gives the same error through the opener as from the verifier reading file by file. And a bucket the producer abandoned is now refused as `stale head: the bucket's head stops at period N while the clock is in period C`, rather than `head file missing: head/updates/1899`, which read like a broken bucket; a hole with later updates present is still `Missing`. The visualizer's chain pane shows that message on the missing period's row.

First live cycle, 2026-11-02, from the Mac, publishing into a local directory (`scripts/dir-publish.sh`; `scripts/r2-publish.sh` is the R2 publisher and was not run). Boundary 13:29:59 UTC, slot 15,566,848. The fetcher dialed from 13:27:59 and had six peers accepted by 13:30:32, out of about 920 dials; every peer held before the boundary was gone by it (four closed, one Nethermind "too many peers"), which is the "peers cannot be held" finding again. The boundary slot was empty: a peer accepted at 13:30:32 answered with blocks either side of it, and the fetcher took the block before, 26,327,404 (slot 15,566,847), 34 seconds after the boundary. Transfer 21 seconds, 141 requests, 17.2 MB, 5 peers seen; 104,584 accounts, 129,635 slots, 2,179 codes. Build 0.5 s. The finality update named the block 788 seconds (13 minutes) after the boundary, with 509 of 512 signers, finalized slot 15,566,847: the missed-slot rule was right. The head step fetched the updates for 1898, 1899 and 1900 (the bootstrap is in 1898) in 2 s; the pre-publish check verified the head to that block and state root through three updates and read 17 accounts, a slot and 3 codes back through it. Publishing was 419 files, 91 MB (86 MB of snapshot, 408 blobs on first publish, 244 KB of head) in 0.9 s to the directory. `check --checkpoint --samples 50` against the published directory: 171 reads, every value verified, absence proven inside the prefix, `Insufficient` outside, 0 wrong. The cycle's end to end was 16 minutes, almost all of it finality. With `--every-mins 60`, R2 holding three snapshots is about 260 MB, and if the producer stops, the last snapshot it published keeps opening for 27 to 55 hours, by where in its period the finality update was signed.

## 2026-11-02: the head's freshness is a rule, and each update file is bound to its period

A review (omp) of the producer loop found that the verifier's freshness was a side effect, and a weak one. It walked period updates from the checkpoint to the clock's period and let helios decide what each file was; helios never sees the file name, and its relevance check compares the update's attested slot with the store's finalized slot. So period 1900's update (attested slot 15,564,866, above its own finalized 15,564,800) served again as 1901, 1902 and every later period was accepted each time, changing nothing, and the period-1900 finality update then verified with the clock any number of periods on: the "abandoned bucket is refused" property the last entry described did not hold against a bucket that replays. And because the walk went to the clock's period, the head a client verified depended on update files the producer rewrites (the current period's best update improves until the period ends), so republishing a period file could invalidate, or move, a head whose `head/finality` had not changed.

The verifier now reads `head/finality` first and takes `s`, the sync period of its signature slot. If `s + 1 < c`, the clock's period, it refuses with `stale head: the newest finality update was signed in period s and the clock is in period c: the producer has not published since`, before reading any period update; if `s > c` it refuses the finality update as from the future (helios's own slot check stays behind it). Otherwise it applies the updates for periods `b` through `s − 1` (`b..s`, b the bootstrap's period), in order, each required, `Missing` if absent (a broken bucket), and none for `s` or later. After them the store holds the committee of `s`, which is all the finality update needs, provided each update carried a quorum and moved the store's finalized header on (helios hands committees over by the store's finalized period, not by the file's name or the period it attests); an update short of that, a genuine one from a finality stall included, leaves the store where it was, and the finality update then fails helios's period check. So the walk fails closed: it can refuse a good head, never accept one under a committee it does not know. Each `head/updates/<p>` must attest a header of period `p`, or it is refused as period `p`'s update whatever it proves. The head returned is the finality update's own finalized header, not the store's, so a period update carrying a finalized header of its own cannot move it.

So "a snapshot lasts until period s+2" is now the rule rather than an accident of which committees helios holds: a head signed in `s` opens through period `s + 1` and is refused from the first slot of `s + 2`, 27 to 55 hours by where in its period it was signed, the same window as before, and no longer extendable by any file in the bucket. Two consequences. The files a head reads, `b..s-1`, were all closed periods when that head was published, and the producer fetches an update once more after its period closes and never rewrites it after that, so a published head's inputs do not change under it. And the current period's update is no longer read by this verifier at all; the producer published it too at first (other light clients follow the chain with it), and since 2026-11-03 publishes only the updates a head it verified read.

The opener's rounds follow: round 1 is the bootstrap and `head/finality`; round 2 the updates `b..s`, with `s` read from the finality update's bytes before they are verified (it only bounds the request; the stale and future checks run on it first, so a bogus `s` asks for at most the periods up to the clock's). When `s = b` there is no round 2. `csl_eth_head::update_periods` now takes both files and returns `b..s`. Tests: a second fixture set, the producer's first published head (bootstrap in 1898, finality signed in 1900, updates 1898 to 1900), which verifies through two updates and reads exactly bootstrap, finality, 1898, 1899; 1900's update replayed as 1899 is refused by its period, and replayed as 1901 and 1902 with the clock in 1902 the head is stale; the 2026-10-31 set's 1897 update in 1898's slot is refused as attesting 1897. Through the opener, every rejection (now 19 cases across both sets) gives the verifier's error in at most two rounds, and the wants per round are exact. The visualizer's chain pane lists only the updates asked for and judges every link from the step the refusal names, accepted before it, unchecked after it; a stale head shows on the finality update's row. `head verify` on the 2026-10-31 bucket now says it was signed in 1898 with the clock in 1900.

The same review corrected three claims of the producer entry above. "A cycle that fails half way publishes nothing a client can see except possibly `latest`" assumed a failed write did not land; a publisher that errors or times out may have written the object anyway, and collection then deleted snapshots by what the state file believed the pointers named. The cycle now journals its intent: before writing `snapshots/latest` it adds the snapshot to `pending` in `state.json`, and only after both `latest` and `head/finality` are confirmed and recorded may it release entries. Releasing all of them then, as first built, assumed a write that timed out was over; a request the store is still serving can land later and name the earlier snapshot again, so since 2026-11-03 an entry is released only by confirmed writes that began at least an hour (or four publisher deadlines) after its own. Collection never deletes a snapshot in `pending`, the ones the recorded pointers name, or the newest by block number; a restart with entries pending keeps them protected until a later cycle commits. Second, fetched head files were marked final before the cycle had verified them, so a bad update from the beacon node would never have been fetched again; now nothing is marked final until the cycle's verification passes, and on a failure the files fetched that cycle (updates, a new bootstrap) are removed from the mirror and `head/finality` there is put back, so the next cycle fetches them again. (As first built, a pass still marked every closed period fetched final, including ones the verifier never read; since 2026-11-03 only the updates it read and checked, `b..s`, are kept, and a bootstrap not yet published is discarded on failure like a fresh one.) Third, a publisher call could hang the loop forever: each call now has a deadline (`--publish-timeout-secs`, 300), runs in its own process group, and past the deadline the group is killed and the call is a failure (which, at a pointer, leaves that snapshot pending). As first built the deadline covered only the program's exit, not the end of its output, which something it started can hold open; since 2026-11-03 it covers both. `produce.log` rotates to `produce.log.1` above 10 MB.

Blob collection stays out, said plainly: blobs are never deleted, locally, in the bucket, or from `state.json`'s list. They are kept for the life of the bucket and nothing bounds them: a blob is a contract's code, the slice's 2,179 codes are 408 distinct blobs, 4.9 MB, and each new contract deployed into the prefix, and each blob a failed cycle uploaded, adds to them for good. How fast that grows has not been measured. A real producer would collect them by mark and sweep: after deleting snapshots, read the code tables of every snapshot still kept (and every one pending), mark the blobs they reference, and delete the rest only if older than the oldest kept snapshot's publish time, so a cycle publishing concurrently cannot lose a blob it just uploaded. And `--every-mins` is a minimum spacing, rounded up to the next epoch boundary, not a period: each cycle fetches at the first boundary at least that long after the last published snapshot's and `--lead-secs` from now, so cycles are 60 to 66 minutes apart when they succeed and a failed one is retried at the next boundary.

Two fetcher fixes came out of the first R2 cycle and the re-run here. The R2 loop's first cycle gave up after 22 minutes holding two peers that both announced block 26,238,405, twelve days old: syncing peers keep their connection, answer every head poll with the same old block, and never serve a recent root, so the fetch never pivoted. A peer whose announced head is more than 15 minutes behind the clock is now closed as soon as its head is read, and the connector dials another, when the pivot is chosen near the head (a peer's head, or the producer's epoch boundary; since 2026-11-03 not for a pivot named by hash or pivot file, which may be older than that and which such a peer may still serve, and for an epoch target measured from the target's time once it has passed); the progress line and the timeout error count dials, accepts and such drops. The first re-run then pivoted with a single peer up and failed two seconds later: one empty answer on a root 15 seconds old counted as "stale on every connected peer". ## 2026-11-03: the producer after a second review: only what verification read, a deadline over the whole call, a grace for late writes

A second review (omp) of the producer found that three of the fixes above held only under assumptions the code did not enforce, and that the fetcher's new peer filter cost more than the entry said. The claims are corrected in place above; this is what changed.

Cache promotion after verification was true in time and not in substance. The verifier reads the updates for `b..s`, `s` the finality update's signing period; the producer fetches through the clock's period, and once a cycle passed it marked every closed period it had fetched final. Across a period boundary those differ: a cycle whose finality update was signed late in period S, with its head files laid out after S+1 began, fetched S's update (closed by then) and froze it unread, and a bad one would have stuck the producer the day a head signed in S+1 needed it. Now `verify` also returns the range the verifier read (`csl_eth_head::update_periods` on the same files and clock), and only updates in it are marked final and published; one fetched for `s` or later is dropped from the mirror and fetched again each cycle, until a head signed after its period reads it. What vouches for a kept update is the verifier's walk: helios checks its signature against the committee the store holds and its proofs, the file must attest a header of its own period, and the head the walk reaches must be our block with the manifest's state root. So the bucket no longer carries the current period's update, which no head of ours reads; a light client that followed the chain with it gets it from a beacon node. The bootstrap had the same gap: one fetched and written to the mirror, then a crash before verification, was read back on restart as trusted, and no later failure removed it. A bootstrap in the mirror that has not been published (which happens only after a cycle verified with it) is now on probation like a fresh one, and removed when a cycle fails.

The publisher deadline covered the program's exit, not its output. A script that starts something in the background and exits (`sleep 86400 & exit 0`) leaves that child holding stdout and stderr, and the producer joined its readers until the child ended. The deadline now bounds the whole call: once the program exits, its readers have until the deadline to see the pipes close; past it the process group is killed, they get two seconds more, and one still blocked (a descendant that left the group) is left detached rather than joined. The exit status decides the call: a program that exited 0 has done its upload, so the call succeeds, and the log says its group was killed. A test runs that script with a one-second deadline: it returns a success once the deadline passes, and the `sleep` is gone. What the deadline bounds is the call, not every resource: a detached reader keeps its thread and its end of the pipe until the descendant holding the other end exits, so a publisher that starts something in a session or process group of its own, inheriting the pipes, and leaves it running would leak two of each per call. Ours do not: `scripts/r2-s3-publish.sh` is a bash script running curl in the foreground, in the group the producer created.

Releasing pending pointers assumed a write that failed was over. Killing the publisher does not cancel a request R2 is still serving, so a `head/finality` PUT for snapshot B that timed out could commit after cycle C's confirmed PUT, after C had released B and collection had deleted it, and the bucket would name a snapshot that is gone. Each pending entry now carries when its writes began (`state.json`'s `pending` is a map from hash to unix seconds; a file with the old list of bare hashes loads with them as begun at load), and a cycle that confirms both pointers releases only entries whose writes began at least the grace before its own: an hour, or four publisher deadlines if longer, against the R2 publisher's curl giving up after 240 s and two retries. Not "older than the grace once some later write is confirmed": a write of B landing after C's would name B again, so the confirmed write is the one that must begin after B's can no longer land. The cycle's own entry stays as well (the pointers name it anyway) until a cycle at least an hour later confirms, so with hourly cycles an entry is released one or two successful cycles after it was written, and collection keeps a snapshot or so beyond `--keep` meanwhile. The grace is an assumption, said plainly: an assumed bound on how late a remote write can land, which nothing in R2 enforces; curl's limits and the publisher deadline end the client's side of a request, not the server's. A write that lands later than the grace after its own start can still name a collected snapshot. The way to enforce it is a conditional write: R2's S3 API takes `If-Match` on a PUT, so each pointer write could require the ETag the producer last confirmed, and a late write would then fail instead of land. That needs the publisher interface to carry ETags, and is not done.

Pending entries also had no bound while pointer writes kept failing: a cycle that uploads everything and then fails at `latest` or `head/finality` adds a protected snapshot, failed cycles are retried at the next epoch boundary, so a pointer write that fails every time (a permission on one key, say) would add one about every 6.4 minutes, each kept for good. Expiring them by age would undo the protection, so instead the producer stops letting new ones in. A cycle first counts the unresolved ones, pending and newer than the snapshot both pointers are confirmed to name, which since the attested tier's review below is the one `latest` names (older ones only wait out their grace; the next confirmed pair releases them, and nothing adds to them). Above three, it fetches nothing: it verifies the mirror's head as of now and, if that reaches the newest unresolved snapshot, publishes the updates it reads (any whose bytes changed) and writes `latest` and `head/finality` for it again, through the same journaled path; the cycle's line carries `pending_error` either way. Everything else of that snapshot is already in the bucket, since an entry is made only after the rest of its cycle went up, and the mirror's head files are the ones its cycle verified unless a later cycle replaced them, in which case the head no longer reaches it. When the retry is confirmed, entries begun more than the grace before it are released and the next cycle is a normal one. When the head cannot be made to reach it (it went stale, or the mirror's head is another block), the cycle goes on and fetches a new snapshot: waiting instead would keep a producer whose pointer writes failed for two days stuck after they work again, since a stale head can never be republished. So under a failure that persists, unresolved snapshots grow by one per head lifetime, 27 to 55 hours, not by one per cycle; that is a bound on the rate, not on the count, and the log says so every cycle.

The fetcher dropped peers whose own head was more than 15 minutes behind the clock in every mode. For a pivot named by hash or through the pivot file, which may be older than that by choice, a peer with a 17-minute-old head may serve an 18-minute-old root, and dropping it could time a fetch out with usable peers in reach. The filter now applies only when the pivot is chosen by time: with no pivot it is measured from the clock, since the pivot will be a recent head; with an epoch target (`--pivot-at`, and the producer) from the target's time once that has passed, and from the clock until then, so a peer whose head is past an 18-minute-old target is kept, as is one that is past the target of a fetch that has been running a while. The producer's dialing before its boundary is unchanged; after it, a peer is judged against the boundary rather than the clock. A named hash or pivot file never drops a peer: one that cannot serve the root answers stale, which the fetch already handles. Blobs, said plainly once more: kept for the life of the bucket, unbounded, not collected.

Tests: only the updates the verifier read are kept, marked final and published, including the rollover (signed in 1899, laid out in 1900: neither 1899 nor 1900 is kept or published, and both are fetched again); pending entries are released only past their grace, by a write begun after it; a `state.json` with bare pending hashes, or none, loads; the background-child publisher returns within its bound, as a success on exit 0 with the child killed, and as a failure with its stderr on exit 4; the peer filter applies for automatic and epoch pivots, measured from a past target's time, and not for a named hash or a pivot file; unresolved pending snapshots are only those past the confirmed head; and with the p1900 head as the mirror's, a stuck snapshot's pointers are written again (updates 1898 and 1899, `latest`, `head/finality`, the older entries released), not when the head is two periods stale, and not for a block the mirror's head does not reach.

## 2026-11-03: the head's two checks that helios keeps for applying an update

The verifier redesign above returns the finality update's own finalized header instead of reading the head back out of a store the update was applied to. That skipped two rules helios enforces only when it applies an update, both found by the same second review. The two-thirds quorum: `verify_finality_update` refuses only zero signers, so one committee member's signature over a fabricated attested header, with proofs of its own making, verified; the verifier now requires 342 of 512 (`has_quorum`). And slot 0: helios reads a finalized header at slot 0 as the genesis sentinel, "nothing finalized yet", and skips its finality branch and execution proof, so a bucket could keep a genuine finality update, set its finalized slot to 0 and write any execution block and state root under it, with no key at all. The verifier now refuses a finalized header at slot 0 or before the checkpoint's slot. The test for it takes the fixture's real finality update, makes exactly that edit, and against the old code got back a verified head with state root `0x1111…`. Both are client-side: the producer's own output was never affected, and the bucket is ours, but a bucket you need not trust is the point.

## 2026-11-03: the attested tier, finality as an upgrade, and FCR as a named source's report

A finalized head is 13 to 19 minutes old the moment it exists, and with hourly cycles the page read state 15 to 80 minutes behind. The producer now publishes every snapshot under the attested head, about a minute or a few after its block, and upgrades it to finalized when finality names it; in the healthy run measured below, reads were 1 to 11 minutes behind on the attested tier (an observation, not a bound: a skipped boundary, a stalled publisher or a missed capture makes it longer), and the finalized tier is still there, 13 to 20 minutes behind instead of 15 to 80.

What the attested tier trusts. `head/optimistic` is a light-client optimistic update: the sync committee's aggregate signature over an attested beacon header, the header's execution payload proven by its execution branch. The verifier walks it exactly as it walks `head/finality` (the same bootstrap, the same freshness rule from the signing period, the same `b..s` period updates; `verify_tier` shares every step but the last), and holds it to the same two checks as the finality update: a two-thirds quorum, 342 of 512, and an attested slot that is not zero and not before the checkpoint's. The execution fields come only from the verified header. The verified head carries its tier, and so does every read: the page says "attested by N of 512, not final, X min old" or "finalized, X min old", and each result says which head it was read against. For a light client the two tiers rest on the same assumption, an honest supermajority of the sync committee; what differs is what the committee signed. A finality update says Casper finalized the block, which reversing would take a third of all stake, slashed. An optimistic update says the committee saw the block as head, and the chain can still reorg it out: a late block, a fork choice that moves, a deeper reorg in a network incident. At an epoch boundary block with 506 to 510 of 512 signing (in the next slot, as observed), that is rare, not impossible, and nothing the client checks can bound it; the page says so under every attested head (`could still be reorged out`), and `?tier=finalized` opens the finalized one.

Why attested rather than FCR. The fast confirmation rule is the better rule, a block confirmed within a slot or two that will not reorg under synchrony, but its verdict is a full node's judgement over all attestations: it needs the fork-choice store's view of every committee's votes, and a light client holds 512 keys and one aggregate signature per slot. There is nothing in FCR a light client can check. So the attested head is the freshest thing this client verifies, and FCR's verdict is shown, when the producer has one, as what it is: the producer's report from a named source. FCR's verdict is a full node's judgement over all attestations; nothing a light client can check; shown as the producer's report from a named source; the public endpoints we tried serve justification, not FCR, as of 2026-11-03.

Concretely, with `--fcr-rpc <url>` or `CSL_ETH_FCR_RPC` (production will use an endpoint whose URL holds a key, so only the URL's host is ever logged, stored in `state.json` or the cycle line, or published; the URL is parsed after the argument parser so no error echoes it), a probe thread polls the source's `safe` and `latest` blocks every 4 seconds from the cycle's start until `--fcr-wait-secs` (600) after the boundary, records when `safe` first reached our block number, takes the source's hash at our height (from that `safe` block when it is at our height, else from a lookup by number) and requires ours (else `conflict`), and classifies the trail, `latest − safe` when it got there: `fcr_like` at 4 blocks or fewer, `justified_like` beyond. A source that fails, hangs or never reaches the block ends at its deadline with its errors counted; it never fails a cycle or holds one up. When it confirms, `head/fcr` is written, after `head/optimistic` and recorded in `state.json`, but only while `head/optimistic` still names that block; a stale note is harmless anyway, since the client reads `head/fcr` in its first round and attaches it only when its block hash and number match the verified head's, as `verified: false`, and never under a finalized head. The page's line is `fast-confirmed per <host> after 13 s (not verified by this client)` or `safe per <host> (justified, not fast confirmation; not verified by this client)`, and nothing when the note is absent or names another block. publicnode's `safe` (ethereum-rpc.publicnode.com) reached our block 386 to 388 s after it, 31 blocks behind `latest`: that is the justified checkpoint, one epoch on, not fast confirmation, and it is reported as such.

Why the pivots stay at epoch boundaries. The finality update names an epoch's checkpoint block, the boundary slot's block or, when that slot is empty, the last block before it, and that is the block the producer already pivots on. So one snapshot serves both tiers: published under the attested head at once, the same files later named by `head/finality`, with no second fetch and no second snapshot. A pivot between boundaries would be fresher by up to six minutes and would never be finalized by name; the finalized tier would need snapshots of its own. The optimistic update for a boundary block is, as observed, the one signed in the next slot (the verifier requires only that its signature slot be after the attested slot), served for about a slot; a thread watches from the cycle's start (every 2 s, keeping per attested block the best participation seen and when it was first seen), stops once the beacon node's head is four slots past the boundary, and the cycle fails if our block was never seen with a quorum by `--attested-wait-secs` (120) after the boundary. A missed capture drops the snapshot rather than publishing it later under finality alone; the next boundary is six minutes away.

Why finality is a watcher and not a step. A cycle used to wait for finality, 13 minutes of its 16. Now a finality watch lives as long as the loop, and between cycles (every 2 s) the loop upgrades `head/finality` to the newest complete snapshot that finality has named: it lays out the head files with the finality update, verifies the finalized head they give as a client would, to that snapshot's block hash and its manifest's state root, journals the snapshot in `pending_final`, publishes any period update the head reads, then `head/finality`. It reads no samples back: the snapshot's files are the ones its cycle sampled through the attested head, unchanged since, and the root they were checked against is the one the finalized head now proves. A failed upgrade is retried after five minutes; finality moving past a snapshot just means the next one is upgraded. So cycles run every epoch, and the two pointers name different snapshots: `head/optimistic` the newest, `head/finality` the one about two to three cycles older. Collection protects every snapshot any pointer or either journal names, and `--keep` (now 10, at least 4) must cover the finality trail: four epochs of trail is 26 minutes. The publish order is runs, manifest, blobs, head updates, `head/optimistic` (journaled), `snapshots/latest`, then `head/fcr`; `head/finality` comes later, from the watcher, through the same verification and its own journal. A `state.json` from before the tier loads: its `pending` entries are copied to `pending_final`, since they were journaled finality writes.

The client tries the attested head first and falls back. Its first round asks for the bootstrap, `head/optimistic`, `head/finality` and `head/fcr`; the second for the period updates either head needs; the third for the manifests of both heads' snapshots, so a fallback costs no extra round. It uses the attested head when it verifies, is newer than the finalized one, and its snapshot's manifest passes the open's checks (since the review below; before, its being in the bucket was enough); otherwise the finalized head; when neither opens, it reports the finalized head's error, unless that is only a missing file and the attested one's is not. `?tier=finalized` or `?tier=attested` forces one.

The snapshot was published under it 68, 307, 158, 130 and 269 s after its block (from the boundaries at 13:55:35, 14:01:59, 14:14:47, 14:21:11 and 14:27:35): the fetch is the whole lag, the pivot found 8 to 58 s after the boundary and 37 to 247 s of transfer with 3 to 6 peers; build 0.5 s, head files 1.3 to 2.1 s, verification and publishing about 2 s.

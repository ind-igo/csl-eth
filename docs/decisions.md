# Decisions

Reasoning that is not in the code. Newest last.

## 2026-10-30: a repo beside cinder, format crates by path

The plan's prerequisite was a second workspace inside the cinder repo sharing its `crates/`. This is a separate repo instead, with `csl-run` and `pgm` as path dependencies on `../cinder/crates/`. The format stays one implementation, which is what the prerequisite was for; the repos stay separate because cinder is a closed PoC with its own chain, harness and results, and the Ethereum work should not churn its history. Cinder has no remote today, so a path dependency is also the only one possible; when either repo gets a remote the dependency becomes a git revision, and a published crate is the end state. `cargo fmt --all` here reaches into the path dependencies and reformats them in rustfmt's default width, which is not cinder's style: run it, then `git -C ../cinder checkout -- .`, or format single files.

## 2026-10-30: the trie crate, before anything else

The profile's claim that needed testing first was "absence from the trie alone, for every shape of miss", and it depends on a builder that emits every node at its position and a walk that returns the shape. `csl-eth-trie` is that, with no file format in it. The builder streams sorted leaves with a stack of open branches; a node is emitted when it closes if its RLP is 32 bytes or longer (or it is the root), and embedded in its parent otherwise, exactly where alloy's `RlpNode::from_rlp` embeds it, so the roots agree with `HashBuilder` on uniform tries from 2 to 5,000 leaves and on crowded tries where leaves, extensions and branches fall under 32 bytes. The walk fetches hashed children by `NodeKey::prefix(path, depth)` and checks keccak before decoding; embedded children are decoded in place under the parent's hash. Every emitted node is on some leaf's walk and every walk touches only emitted nodes, checked in `tests/roundtrip.rs`. A node deeper than 62 nibbles cannot be keyed (`TooDeep`), which the producer treats as an abort; real keccak paths never get there and the synthetic tests had to be told so.

## 2026-10-30: `csl-run` grew the variable layout, in cinder

Core §3.2's variable layout and `inline_proofs = false` are implemented in cinder's `csl-run` (its `docs/decisions.md`, same date), additively: `Format { layout, inline_proofs }`, `with_format` constructors, `Page::encode_with` / `decode_with`, `Layout::try_new_with`, `Reader::get_entry`; `pgm` gained `Grouper::push_at` and `Fitter::finish_with` because a variable run knows its page count only when the last page closes. v1-min's signatures and `Lookup` are unchanged and cinder's chain passes. A variable layout with inline proofs is refused by the writer: a record's size would depend on the page count. The run's identity is `blake3` of the file, computed by a read-back pass at `finish`. Conformance vectors and the TypeScript harness do not cover the variable layout yet; they are this repo's to add once the format settles on mainnet shapes.

## 2026-10-30: blob threshold 3,968, not the profile's 4,096

A tag 0 value alone on a page can be at most `4096 − 66 − 2 − 32 − 1 − 2 = 3,993` bytes (`csl_run::MAX_INLINE_VALUE`). Core §3.2 says blobs start above 3,968; the profile's "4,096" cannot fit a page. `CODE_BLOB_THRESHOLD = 3968`. The profile text should be corrected to core's figure.

## 2026-10-30: the manifest is JSON and nothing signs it

Cinder's `Manifest` and `ColdRoot` carry base, delta and rebuild semantics and a sealer signature, none of which applies: nothing anchors a run root on Ethereum and the client's single trust input is the `state_root` it verified. The snapshot manifest (`snapshots/<block_hash>/manifest.json`) names the execution block hash, number, timestamp, `state_root`, the covered prefix, and one `RunRef` per non-empty table (`csl_run::RunRef` with `block_lo = block_hi = block_number`). `snapshots/latest` holds the newest block hash. `Snapshot::open` takes the caller's verified `state_root` and refuses a manifest that claims another, rather than walking files that cannot verify and reporting them `Insufficient` one key at a time. An empty table has no run (csl-run's rule), so a slice without code or storage has three files, not four; the client answers `NoTable` for it.

## 2026-10-30: the producer sorts in memory

Nodes are collected in vectors and sorted before writing: a 1/256 mainnet slice is a few million nodes, a few GB at most, and the milestone 1 machine has 64 GB. Milestone 4's full export (about 1.5 × 10^9 nodes) needs the external sort cinder's sealer already has, behind the same `produce` call. The producer checks every storage root against its account's leaf, the account root against the header's `state_root`, every `codeHash` against its bytecode, and writes nothing until all three hold; an account with no storage stream must carry the empty root. The content-addressed fourth table (`keccak(node) → node`) is written from the same nodes, deduplicated, for the serial baseline of profile §9, but no client reads it yet.

## 2026-10-30: what the first end-to-end run measured

`crates/client/tests/e2e.rs` on 3,000 synthetic accounts (leaves at depth 3, so speculation to depth 9 wastes six lookups per read; mainnet leaves sit at 7 or 8 and waste two).

- **Every shape.** 3,000 present accounts verified; 1,000 random absent keys split 608 `EmptySlot` and 384 `LeafMismatch`, plus a crafted 60-nibble extension giving `ExtensionMismatch`, `EmptySlot` under its branch and `LeafMismatch` at its leaf; 19,968 present storage slots and an absent slot per trie; empty storage answered without a storage request; code inline (375) and as blobs (375); `KECCAK_EMPTY` with no fetch; an unknown `codeHash` is `Insufficient(Missing)`.
- **Faults.** 40 random bit flips per table in six rounds, a truncated table, a dropped page served as a short read, a table from a different trie under the real `state_root`: every read was the right answer or `Insufficient`, none was a false absence or a wrong value. A table the manifest names but the bucket lacks fails `open`.
- **ε against requests.** The reader's walk after a prediction is sequential: each page the prediction is off is a dependent request. With the same 170-page account table, ε = 1 (model 172 B) gave a mean 14.2 requests and 58 KB per present account read over ten speculated depths, 1.42 per lookup, every walk one page; ε = 2 and ε = 4 both fit one segment (28 B) and gave 16.5 requests and 68 KB, 1.65 per lookup, with walks of up to 4 pages. The profile's "about nine page requests, 40 KB, one round" assumed a direct hit per depth. Consequences: `produce` takes ε as an option and the default stays the profile's 4 until mainnet shapes are measured; the client should learn the leaf depth from its first reads and stop speculating past it; and for the deepest depths a two-page range (`p`, `p + 1`) buys subtree contiguity for one request. The 50 KB budget is not asserted by the tests; it is milestone 1's exit on real shapes.

## 2026-10-30: range proofs are verified by rebuilding, and the proof is the boundary

A snap `AccountRange` response is consecutive leaves from `origin` plus the Merkle proofs of the origin path and the last leaf's path. The usual verifier (geth's `VerifyRangeProof`) stitches the proof nodes around the leaves and hashes up. `csl-eth-trie` instead reads the two proof paths once, collecting the child references that stand for everything *left* of `origin` and *right* of the last leaf (`walk_side`), and feeds those references and the leaves through the same streaming builder that produces runs, now able to `push_sealed(path, RlpNode)`: a sealed subtree is a parent's child slot standing for a subtree whose contents are not here. The rebuilt root must equal `state_root`; the slice is `more` when anything is sealed to the right. One builder for production and verification is the point: the sealed references the verifier collects for the first and last chunk of a slice are exactly the boundary the producer needs to build the slice's leaves up through the ancestors to `state_root`, so `ProduceOptions::boundary` takes them unchanged and the producer's existing root check becomes the slice's proof of membership. The ancestors emitted are the root, the branch at each depth along the prefix path, and the branch the first leaf past the slice hangs under (snap returns that leaf, the slice drops it, its sibling reference is kept). Keys outside the prefix walk to a sealed slot and end `Insufficient(Missing)`, never in an answer: `crates/client/tests/slice.rs`. A sealed path nested inside another, or out of order, is refused by the builder; a boundary with a reference altered or dropped fails the `state_root` check.

## 2026-10-30: snap/1 and snap/2 both offered, eth and snap multiplexed by hand

reth 2.9.0's `EthSnapStream` requires exact snap/2, but mainnet peers still answer snap/1 (geth 1.16, Nethermind 2.2 in the first probe), and the six message ids are the same in both. The peer offers eth/68, eth/69, snap/1, snap/2 in `Hello`, takes whatever is shared, and drives the `P2PStream` itself: eth frames from id 0, snap frames from `eth.num_messages()` as reth's `relative_message_id_offset`, snap's own id byte rebased on the way out. Inbound requests from the peer (headers, bodies, transactions, receipts, snap) are answered empty so the connection stays useful; everything undecodable is ignored rather than fatal.

## 2026-10-30: the pivot is self-consistent, not yet verified

The fetcher pivots on the first usable head a peer announces: the peer's `Status` block hash, the header fetched by that hash, checked to hash to it, and recent (number past the fork head and timestamp within fifteen minutes; a syncing geth announces genesis). That ties the slice to a header some peer claims is canonical, not to a verified one. The head verifier over light-client files (`helios-consensus-core`) is the next piece; until then a slice's `head.json` is "the state at this hash as the network served it", and the producer's `state_root` check is the only verification. `--pivot <hash>` exists so a run can be pinned to a hash chosen out of band.

## 2026-10-30: re-pivot keeps storage and code by their own roots

snap peers serve roots from about the last 128 blocks. A 1/256 slice at today's state is tens of thousands of requests, more than a window at a moderate peer count, so the fetcher expects to re-pivot: when three peers (or every connected peer) answer an account range with "no such root", the pivot moves to a fresh head, every account sub-range starts over, and the storage tries and bytecodes already fetched are kept, keyed by storage root and code hash respectively, since they are content-addressed and an unchanged account still references them. Only account ranges are redone. Account ranges are split sixteen ways on the nibble after the prefix so eight peers work in parallel on one root; a sub-range's chunks are contiguous, so its left and right boundaries are the first chunk's left and the last chunk's right.

## 2026-10-30: the slice on disk is separate from the bucket

`csl-eth fetch` writes a slice (`head.json`, RLP files of accounts, storage by root, code, and the boundary) and `csl-eth build` turns it into a bucket. Two steps because fetching takes minutes to hours and depends on the network while building is deterministic and seconds; a slice can be rebuilt with another ε or table layout without re-fetching, and the measurements of milestone 1 compare builds of one slice.

## 2026-10-30: the first mainnet slice, and what it cost to read

`csl-eth fetch --prefix 1a7` (1/4096 of state) at block 26,305,903, state root `0xe8e6…5800`, from one Nethermind peer: 104,361 accounts, 3,362 distinct storage tries (6,878 by account; proxies share roots) with 129,555 slots, 2,168 bytecodes, 17.9 MB over 133 requests, no re-pivot. Transfer took about two minutes; the other two were spent finding a peer. Getting peers is the slow part: of 355 dials in a 100 s probe, 155 answered "too many peers", 81 timed out, 58 reset, 21 had no snap, and 3 handshook. Dials now run 192 wide with a 10 s dial timeout, candidates are deduplicated by address as well as node id (a crawler answers from one address under fresh keys), and an idle peer is kept polled so its pings are answered; before that, geth dropped us for "ping timeout" while we waited for a pivot. A syncing peer announces genesis as its head and is not a pivot candidate.

`csl-eth build` turned the slice into a bucket in 0.4 s with 102 sealed subtrees in the boundary and the account root equal to the header's `state_root`: the slice is the network's state at that block, proven. 144,964 account nodes in 5,557 pages (22.8 MB), 180,808 storage nodes (20.3 MB), code 1.4 MB plus 407 blobs, the content-addressed table 42 MB. Mainnet account leaves sit at depth 8 (9 nodes walked, p95 10), storage leaves 10 to 12 nodes deep under the account.

`csl-eth check` reads the bucket with the client, 300 sampled accounts with their slots and code, absent keys inside the prefix, keys outside. Every value verified, every inside absence was proven by the trie, every outside key ended `Insufficient(Missing)` after a repair round at the sealed slot, at every ε. The cost, mean per account read, speculating depths `0..=8`:

| ε | model | requests | KB | slot read requests / KB |
|---|---|---|---|---|
| 1 | 3,076 B | 13.4 (p95 16) | 53.5 | 25.4 / 101 |
| 2 | 748 B | 18.7 | 74.6 | 32.5 / 130 |
| 4 | 220 B | 27.0 | 108 | 46.3 / 185 |
| 8 | 52 B | 41.0 | 164 | 78.1 / 312 |
| 16 | 52 B | 61.5 | 246 | 111.5 / 446 |

Speculating to depth 9 instead of 8 adds about 1.4 requests and 5 KB. The profile's "about nine page requests, 40 KB, one round" is not met by any ε: the rounds are right (1.0 to 1.1), the requests are not, because each page of model error is a dependent request on the sequential reader, as the synthetic run already showed. ε = 1 is now the default: its model is 3 KB for 145,000 nodes, which is nothing. The remaining gap to the profile's figure is the lookups themselves, nine per read, and that is where the next client work is: the top levels of the trie are the same nodes for every key (one root and one node per depth along the prefix here; 1 + 16 + 256 + 4,096 nodes for the top four levels of full state), so a client that keeps them after its first reads speculates from depth 4 and pays five lookups, and a `(p, p + 1)` range for the deep depths buys a prediction miss for one request. Both are measurements for the next stage, not changes to the format.

## 2026-10-31: the per-snapshot budget, and what the HTTP bucket showed on loopback

Two budgets, not one. Resident memory for a light client can be a few MB without anyone noticing; what cannot is bytes per snapshot for a client that follows the chain, because the model changes with every snapshot and milestone 2 snapshots every finalized checkpoint, about 225 a day. Extrapolating this slice's model bytes per page (0.55 at ε = 1, 0.13 at ε = 2, 0.04 at ε = 4) to mainnet's roughly 16 million account pages and 65 million storage pages gives models of about 45 MB, 11 MB and 3 MB per snapshot. The plan now says: under 1 MB per snapshot for a following client. ε = 1 stays the default because its model need not be downloaded whole: the keys are keccak hashes, so the model's segments are nearly evenly spaced in key space and the section covering a key can be predicted from the key and fetched as one small range in the same round as the pages. That is a reader change in csl-run, not a format change, and it is the next client lever to build.

`csl-eth check --url` reads a bucket behind HTTP (`HttpBucket`: files by GET, runs by `Range`, an optional proxy for tunnelled hosts). A `Prefetch` hint on the source lets the snapshot hand it the predicted page of every speculated depth before the round, fetched over threads; a source keeps one read's pages and forgets them when the next read starts (`forget`), so nothing is cached across reads and every read is measured on its own. R2 is not enabled on the account and writes to fafo-0 were not permitted in this session, so the measurement so far is loopback through caddy, which says nothing about latency (0.4 to 1 ms per read) and everything about requests on the wire:

| account read, ε = 1, depths 0..=8 | HTTP requests | KB | dependent requests after the round |
|---|---|---|---|
| sequential, pages kept for the read | 6.7 (p95 8) | 27 | all 6.7 |
| prefetch the predicted page per depth | 6.7 (p95 8) | 27 | 1.3 (p95 3, max 3) |
| prefetch predicted ± 1 | 12.0 (p95 13) | 48 (p95 52) | 0.0 (max 1) |

The reader's logical count was 13.4 lookups; on the wire it is 6.7 pages, because the table's order is pre-order: a node's key is its path, so a node sorts immediately before its subtree, the depth-7 node and its sixteen depth-8 children share a page, depths 5 to 8 of one path sit within a few pages, and in a slice the ancestors above the prefix sit together on the first page. The reader has no page cache, so before this it fetched the same page once per depth. Prefetching one page each side of every prediction makes the read one round for 12 requests and 48 KB, which is the profile's "one round, 40 KB" within a few KB on mainnet shapes; the mean is under the 50 KB rule and the p95 is not. Storage reads are over it: 19 requests and 76 KB sequential, 36 and 146 KB at ± 1, because the slots sampled sit 10 to 12 nodes deep in the largest contracts. Still to measure, in order: a two-page range (`p`, `p + 1`) per prediction as one request, which should give one round at about 5.5 requests and 44 KB; the model section by key; the top levels kept across reads; and all of it against a remote host, where the rounds become milliseconds.

## 2026-10-31: the same reads against R2, where the rounds become milliseconds

The ε = 1 bucket (413 files, 90.7 MB) is on Cloudflare R2 behind its r2.dev domain, bucket `csl-eth-apac`. The first attempt landed in WEUR because the location hint was a guess; a deleted bucket's name keeps its old region when recreated, so the APAC bucket has a new name and `csl-eth` is retired. The client ran on a Mac in Taipei behind a Mullvad exit in Manila, served by Cloudflare's Hong Kong colo: one range request is about 110 ms at the median (the outside-prefix reads, one page each, measure it), which is a slow path, not a fast one, and that is the point of the table. 40 to 60 sampled accounts per mode, speculating depths `0..=8`, every value verified, zero wrong or unexpected:

| account read, ε = 1 | HTTP requests | KB | dependent | ms p50 | ms p95 |
|---|---|---|---|---|---|
| sequential | 6.3 | 25 | 6.3 | 829 | 1,110 |
| prefetch the predicted page per depth | 6.9 | 28 | 1.4 (max 3) | 286 | 506 |
| prefetch predicted ± 1 | 12.1 | 50 | 0.0 (max 1) | 179 | 936 |

Storage slot reads, two samples each, deep slots in large contracts: 4.1 s sequential over 19 requests, 1.1 s with the predicted pages prefetched (5 dependent), 0.8 s at ± 1 over 38 requests and 150 KB. Code: one or two requests, 100 to 200 ms.

What it says. Sequential reading is the round-trip count times the round trip: 6.3 requests at about 130 ms is the 829 ms seen, and nothing about the format fixes that, only fewer dependent requests do. Prefetching the predicted page takes the dependent chain from 6.3 to 1.4 and the read from 829 to 286 ms, without a byte more on the wire; the remaining 1.4 are model misses at the deep depths, and they cost a round each. Prefetching ± 1 removes the last dependent round for 22 KB more and gets the median to 179 ms, about 1.6 round trips: one for the parallel fan-out and the rest is the slowest of 13 connections. Its p95 is worse than the predicted-page mode's, 936 against 506 ms, which the loopback run could not show: the fan-out is 13 parallel HTTP/1.1 requests on 13 connections (ureq has no HTTP/2), so one slow connection, or a fresh TLS handshake through the VPN, holds the whole round. The lever here is not fewer pages but fewer connections: HTTP/2 multiplexing, or the two-page range per prediction that halves the request count to about six for the same bytes. Both are client changes; the first is a dependency choice, the second was already next on the list and now has a second reason.

Against the budgets: 50 KB per account read at ± 1 is the profile's figure on mainnet shapes, and 180 ms through a VPN to another country is a read a wallet can wait for. Storage is still three times over, and it is the depth of the slots, not the format, which the top-level cache and the two-page range should both help. The one-round claim is now measured end to end: a client with the model in hand reads any account in the slice in one parallel round against a public bucket, with no node anywhere.
